# DILU (experience memory with reflection) in REVOKE

**Method.** DiLu (Wen et al., ICLR 2024) equips an agent with a memory of past *experiences*: after each task the trajectory is reflected into a concise summary, stored under the task description, and at a new task the most similar past experiences are retrieved as few-shot guidance. We run EvolveLab's implementation from MemEvolve (`EvolveLab/providers/dilu_memory_provider.py`, commit 6035d56, Apache-2.0), vendored byte for byte under `eval/memory/vendor/dilu/` and wrapped by `eval/memory/dilu.py`.

**What it stores.** One entry per completed task: the task text (embedded, the retrieval key) and an LLM-written "ultra-concise" step-by-step summary (max ~150 words) of the trajectory, produced by the upstream summarisation prompt. Entries are never merged, rewritten or forgotten; the store grows by one per task and, with `--persist`, across the episodes of a world.

**When it writes.** Only at `record_action`, i.e. once per task, after the agent has acted. The trajectory handed to the summariser is: the most recent sessions that have left the raw window (a rolling buffer of 4 sessions, at most 6000 characters, as "context"), the task message, the action taken, and the agent's stated rationale. Sessions that scroll out of the window are *not* summarised individually -- DILU learns from task trajectories, not from passing text -- so `observe` is free and the system makes exactly one backbone LLM call per task.

**How it reads.** At every task, `recall` embeds the task text (local embedder, shared with every other system), takes the single nearest stored experience by cosine similarity (k = 1, upstream's setting, no similarity threshold) and places it in the prompt framed as upstream's agent does: "Memory System Guidance / Below is the trajectory from a similar task: ... End of similar task trajectory", clipped to the recall budget. Nothing is returned until the first experience exists.

**When the summary comes back empty.** `LLM.text` returns `''` on any API failure, and a reasoning-enabled backbone can spend its whole `max_tokens` budget on reasoning before emitting any content. Upstream then stores the *full reconstructed trajectory* as the experience -- here a slab of raw transcript (~6.6k characters of rolling session buffer) -- and because `recall` clips from the tail, one such entry crowds every later experience out of the prompt. REVOKE instead stores a short deterministic stub built only from the task text (already the embedded retrieval key) and the action taken, with no session text, and counts it in `stats()` as `summaries_empty` (or `summaries_error` when the call raised), both included in `summaries_fallback`, so a run can be audited for how many of its experiences are stubs. `summary_max_tokens` also defaults to 2000 rather than 600, so a reasoning backbone has room to reach the ~150-word summary.

**Adaptations.** (i) The summariser's LLM calls and the embedder run through the shared backbone/embedder objects, so cost is counted and no separate model is involved. (ii) Upstream labels each trajectory `Correctness: Correct|Wrong` from a judge against the gold answer and asks the summary to explain the success/failure reason; REVOKE provides no correctness signal during an episode, so those two lines of the prompt read "Unknown (no feedback is available)" and ask what was chosen on what stated grounds. Everything else in the prompt is verbatim. Consequently DILU here cannot distinguish good from bad experiences: every past action, violation included, becomes a candidate exemplar for the next similar task. (iii) The JSON store on disk is disabled (in-process only; opt-in write for inspection), and upstream's hard dependencies on scikit-learn and sentence-transformers are made optional.
