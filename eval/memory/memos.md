# MemOS (`--memory memos`)

**System.** MemOS (Li et al., 2025, arXiv:2507.03724), official repository MemTensor/MemOS at commit 176d4f6, installed from PyPI as `MemoryOS==2.0.33`. We run the library's own textual-memory pipeline -- `GeneralTextMemory` with its extraction prompt (`SIMPLE_STRUCT_MEM_READER_PROMPT`), its `TextualMemoryItem` schema and its `QdrantVecDB` store -- imported and wrapped, not re-implemented.

**What it stores.** Memory items extracted by the backbone from departed sessions: each item is a self-contained third-person statement (`value`) with a short title (`key`) and thematic `tags`, embedded with the harness's local embedder and kept in an in-process Qdrant collection (cosine). The agent's own action at each task is also stored verbatim as one item, as `MOS.add(memory_content=...)` does for a `general_text` cube. Metadata carries the world as `user_id` and the source session index as `session_id`.

**When it writes.** Sessions leaving the raw window are buffered up to 1,024 tokens (the MemReader's chat-window size) and extracted in one LLM call; the buffer is also flushed before every recall and at the end of an episode. One extraction call per ~1-2 sessions. If the model's reply is not the expected JSON, the reply is re-read with MemOS's own parser tolerating a missing key/tags; if it has no memory list at all, the raw window is stored as a single item, which is the MemReader's own fallback. No further LLM calls are made.

**How it reads.** At a task, `GeneralTextMemory.search(task_text, top_k=12)`: embed the task, nearest neighbours by cosine, ranked by score. The memories are placed in the prompt as MOS's `_build_system_prompt` formats them -- a numbered list under `## Memories:` -- and cut to the recall budget by dropping the lowest-ranked items.

**Adaptations.** (1) The MOS facade (SQLite user manager, MemCube registry, scheduler, chat loop) is not instantiated: for a `general_text` cube `MOS.add`/`MOS.search` merely dispatch to `text_mem.add`/`.search`, and the facade needs a SQLite database and a tokenizer download. (2) MOS itself only runs the LLM MemReader for the Neo4j-backed `tree_text` memory and stores strings verbatim in `general_text`; here sessions do go through `GeneralTextMemory.extract`, which uses the same MemReader prompt, so the system under test is MemOS's extraction-then-retrieval pipeline rather than raw chunk retrieval. (3) The LLM and embedder are MemOS backends registered in its factories that delegate to the shared backbone and local embedder; the vector store opens Qdrant with `location=":memory:"` and is otherwise unchanged. (4) Multi-speaker session text is handed to the extractor as a single user message, MOS's convention for plain strings.

**Consequences for REVOKE.** The `general_text` pipeline has no deduplication or conflict resolution (that lives in the `tree_text` reorganiser, which needs Neo4j), so a rule and its later revocation coexist as separate items and both can be retrieved; ordering is by similarity, not by time, unless `show_session` is enabled. MemOS receives no correctness signal and has no branch that would use one. `persist` keeps the collection across the episodes of a world; a non-persistent episode starts by dropping and recreating it (`delete_all`).
