# Appendix · The six memory systems under test

## The harness

Every memory system reaches REVOKE through one Python class with six methods (`eval/memory/base.py`). `begin_episode` hands the system the blind view of an episode — transcript, tool schema, option lists, never a label — and says whether it may keep what it learned from the world's previous episodes. `observe` is called once for each session block that has left the raw context window for good (the runner keeps the most recent `--window` tokens verbatim, 8,000 by default). `recall` is called at each probe and returns whatever text the system wants placed in the prompt, bounded by a recall budget of 4,000 tokens by default. `record_action` reports the tool call the backbone made and the reasoning it stated, and nothing else. `end_episode` exists for between-episode consolidation, and `stats` returns the counters written into the trace. Every LLM call a memory system makes for its own purposes — extraction, curation, summarisation, poignancy scoring, reflection — goes through the same `LLM` object as the agent's own acting calls, so it runs on the backbone under test and its input and output tokens are counted in the episode's cost; embeddings are computed locally (sentence-transformers where installed, otherwise a deterministic hashed bag-of-words), never through the API, so no system pays for its retrieval in backbone tokens and no embedding leaves the process. No correctness signal ever crosses this interface: `record_action` carries the action and the rationale but no verdict, because REVOKE grades the trace only after the episode has finished, against the derivation layer rather than against anything the agent was told. Finally, `--persist` runs a single backend instance over all the episodes of one world in manifest order, so whatever a system consolidates carries forward from episode to episode; without it, each episode starts from an empty store. This is the setting in which "more experience, more violations" is measured.

## mem0

mem0 (Chhikara et al., 2025, arXiv:2504.19413) is declarative middleware: conversation turns are passed to an LLM that extracts short natural-language facts, which are embedded into a vector database scoped by user, and a later query retrieves the nearest facts. The adapter imports the installed release `mem0ai==2.1.0` rather than re-implementing it, and subclasses mem0's own LLM and embedder interfaces so that every extraction call runs on the backbone under test and every embedding is local; the store is mem0's own Qdrant wrapper on an in-memory client, and its history and message tables live in SQLite `:memory:`. At `observe` each departed session goes through `Memory.add(..., infer=True)` under the world's `user_id`, with the runner's session index in the metadata; two write pipelines are offered, `additive` — what a default install runs, one LLM call carrying a 33,653-character static extraction prompt plus the nearest existing memories and the last ten message rows, and add-only, never rewriting or deleting what is already stored — and `reconcile`, a port of the paper's two-phase extract-then-ADD/UPDATE/DELETE/NONE pipeline from mem0ai 1.0.11, the last release that shipped it, at two calls per session (one when extraction yields no facts). At `recall` the probe text is searched with `top_k` 12 and mem0's own threshold of 0.1, and the hits are rendered one per line, tagged with the session they came from. `record_action` writes the action through mem0's raw `infer=False` path with no LLM call. Two deliberate departures from library defaults are worth naming: `top_k` is 12 rather than upstream's 20, so that mem0 and MemOS are compared at equal retrieval depth; and the probe text is by default not spliced into the action memory, because REVOKE probes within a world are near-identical in wording, so an action memory carrying the probe text is by construction the nearest neighbour of every later probe and evicts the extracted session rules from `top_k` — an adapter artefact rather than a property of mem0, measured at 47% of recalled lines being the agent's own actions with the probe text included against 24% without. Nothing in either pipeline branches on task success and no correctness signal is inferred, so the blind protocol changes nothing about how mem0 behaves; what it leaves in place is that mem0 cannot order a rule against its later revocation by time, since `created_at` records the wall-clock moment of the write rather than the in-world session, and only the session index in the metadata recovers chronology at all.

## MemOS

MemOS (Li et al., 2025, arXiv:2507.03724) presents memory as an operating-system layer over several memory types; the textual pipeline under test extracts self-contained third-person statements from a conversation, each with a short title and thematic tags, embeds them and retrieves by cosine similarity. The adapter imports `MemoryOS==2.0.33` and runs `GeneralTextMemory` with its own `SIMPLE_STRUCT_MEM_READER_PROMPT`, its `TextualMemoryItem` schema and its `QdrantVecDB`, with the LLM, embedder and vector-store backends registered in MemOS's own factories; the MOS facade is not instantiated, because for a `general_text` cube `MOS.add` and `MOS.search` are thin dispatchers to the cube's own methods and the facade additionally wants a SQLite user database and a tokenizer download. At `observe` departed sessions are buffered to the MemReader's 1,024-token chat window and extracted in one call, the resulting items are embedded and upserted; `recall` flushes the buffer, searches with `top_k` 12, and renders the hits as MOS's own numbered `## Memories:` list under `_build_system_prompt`'s base prompt, dropping the lowest-ranked items until the block fits the budget; `record_action` adds the action as one verbatim item, exactly as `MOS.add(memory_content=...)` does, with no LLM call. Three deviations were forced. First, MOS runs the LLM MemReader only for the Neo4j-backed `tree_text` memory and stores `general_text` strings verbatim, so sessions are put through `GeneralTextMemory.extract` explicitly — otherwise the condition would be raw-chunk retrieval rather than the extraction-then-retrieval pipeline the paper describes. Second, `GeneralTextMemory.extract` raises on JSON its parser cannot read, where MemOS's own MemReader salvages the text, so a malformed reply is re-parsed leniently, then salvaged entry by entry, and only as a last resort stored as a single raw item; an *empty* reply is treated differently and dropped, because an empty reply means the backbone call exhausted its retries, and salvaging an API failure would quietly convert this condition into raw-transcript retrieval. Third, the recall header is `_build_system_prompt`'s base prompt with only its closing sentence removed — the instruction to reference memories naturally without mentioning them, which has nothing to govern when the agent acts by calling a tool — and nothing task-specific is added, in particular nothing naming rules or what is currently in force. MemOS has no branch anywhere in this pipeline that reads task success, so the absent correctness signal costs it nothing; what does matter for REVOKE is that the `general_text` path has no deduplication or conflict resolution, since that lives in the `tree_text` reorganiser and needs a Neo4j server, so a rule and its later revocation coexist as separate items and both can be retrieved, ranked by similarity rather than by time.

## Generative Agents

Generative Agents (Park et al., 2023) keep a memory stream of timestamped natural-language nodes, each scored for poignancy, and retrieve for a focal point by a weighted sum of recency, importance and relevance; when accumulated poignancy crosses a threshold the agent reflects, asking itself salient questions about its recent memories and writing the answers back as higher-level thoughts that point at their evidence. The paper's own code is implemented here rather than EvolveLab's "generative" provider, which ingests whole task trajectories, tells its summariser whether the trajectory was correct and retrieves only successful cases — neither the memory stream nor the reflection of the paper, and dependent on a signal REVOKE never gives. At `observe` every non-empty line of a departed session becomes exactly one event node, embedded locally and scored 1–10 with the original `poignancy_event_v1` prompt; `record_action` writes the agent's tool call and stated rationale as an action node, scored with the next batch; `recall` runs `new_retrieve` with the probe text as focal point, min-max normalising recency, relevance and importance over the whole stream, combining them with the shipped weights 0.5 / 3 / 2, showing the top 30 nodes oldest-first with their session numbers and marking them accessed. Reflection follows `reflect.run_reflect` exactly: three focal questions drawn from the most recently accessed nodes, thirty nodes retrieved per question with all retrieval finished before the first insight is written, five insights with evidence per question, each scored and stored as a thought whose depth is one greater than its deepest evidence. Three adaptations were forced by the harness rather than by the method. Poignancy is asked for a whole session in one call returning a list instead of one call per event, with a fixed `[5, 2, 7]` example and the required length stated in the instruction, because padding the example out to the batch size with the fail-safe value 4 anchored long sessions onto a constant score. Every memory call is given at least 600 completion tokens, because the harness backbone defaults to low reasoning effort and reasoning tokens count against `max_tokens`, so the original's 30–60 token cap returned nothing at all and silently made every score the fail-safe; `stats()` therefore also reports `empty_replies` and `score_failsafe`, so a truncated or failing run is visible rather than merely flat. Recency uses the paper's stated time-since-access semantics rather than the shipped code's rank-based variant, which as written gives the oldest node the highest recency. Nothing in Generative Agents branches on task success — reflection reads the stream, never a reward — so REVOKE's missing correctness signal changes nothing about how the system behaves.

## Dynamic Cheatsheet

Dynamic Cheatsheet (Suzgun et al., 2025, arXiv:2504.07952), in its cumulative variant DC-Cu, keeps no store of episodes at all: a single evolving free-text cheatsheet is rewritten in full after every query by a curator that sees the previous cheatsheet, the current input and the model's own answer, and anything the curator does not copy forward is lost — a consequence the original prompt warns the curator about explicitly. The roughly thirty lines of the DC-Cu branch of the authors' `advanced_generate` are re-implemented on the harness LLM, because their `LanguageModel` constructs its own provider client from keys in a config file and would break the rule that every system runs on the backbone under test; the cheatsheet extractor is copied from source. In REVOKE the curator's "current input" is the span of transcript that has just left the raw window and its "model answer" is the act-tool calls recorded since the last update, so `observe` batches departed sessions and runs the curator once per two distinct ones, `record_action` appends the probe, the tool call and the stated reasoning to that batch as the model's actions, and `recall` first curates anything still pending and then places the whole cheatsheet in the prompt framed as the authors' generator prompt frames it. The curator prompt is the original text with its solution, code and Python vocabulary reworded to rules, rulings and decision patterns, its question tags renamed to session tags, the two code-specific bullets dropped, the word budget computed from the 12,000-character cap, and one parenthetical line added to each of the two input slots saying what they now contain; the structure, responsibilities, principles, `memory_item` format and loss warning are untouched. One behavioural fix was made to the vendored extractor: upstream takes everything after `<cheatsheet>` and before `</cheatsheet>` by splitting on each tag in turn, so a reply the completion cap cut off after the opening tag has no closing tag to split on and the whole accumulated cheatsheet is replaced by the fragment — one truncated call can wipe the sheet. Here a well-formed closing tag is required before anything is replaced, and both an unclosed block and a block that closes empty keep the previous cheatsheet, which is the extractor's own fallback for a reply with no block at all; the occurrence is counted so it can be audited. Dynamic Cheatsheet is the one system whose original design already has no correctness signal, since the curator is asked to assess the model's answer itself, so the adaptation is only a change of wording — from assessing the correctness of the provided solution to assessing the model's actions with no verdict available, and from a usage counter of "successfully used in problem-solving" to "used to act on a task" — but the consequence is the same as in the original: a wrong action can be curated into the cheatsheet as a worked example, and nothing in the method will later mark it wrong.

## DILU

DiLu (Wen et al., ICLR 2024, arXiv:2309.16292) equips an agent with a memory of past experiences: after each task the trajectory is reflected into a concise summary, stored under the task description, and at a new task the most similar past experience is retrieved as few-shot guidance. EvolveLab's implementation from MemEvolve is vendored byte for byte and wrapped, with four seams overridden — the LLM callable, the embedding model, initialisation, and JSON persistence, which is disabled so that a fresh backend never inherits an earlier run's store — leaving the retrieval, write and prompt logic upstream's own. `observe` makes no call and no write, because DILU learns from task trajectories rather than from passing text; a departed session only enters a rolling buffer of four sessions and at most 6,000 characters that becomes the "context" step of the next trajectory. `recall` embeds the probe text, takes the single nearest stored experience by cosine similarity, and frames it as upstream's agent does. `record_action` is where the system's only LLM call happens: the trajectory — buffered context, probe, action, rationale — goes to upstream's summariser, which writes an ultra-concise step-by-step summary of at most 150 words, and the pair is appended with the probe embedding as the key. The forced deviation is the outcome. Upstream reads `metadata["is_correct"]`, set by a judge model against a gold answer, writes `Correctness: Correct` or `Correctness: Wrong` into the summarisation prompt, and asks the summary to close with the success or failure reason; REVOKE passes no such signal, and upstream's default for a missing flag is `Wrong`, which would stamp every experience a failure. Those two lines therefore read "Unknown (no feedback is available)" and ask instead what was chosen and on what stated grounds, with everything else in the prompt verbatim — so DILU here cannot separate good experiences from bad, and every past action, violation included, becomes a candidate exemplar for the next similar probe, which is precisely the failure mode REVOKE sets out to measure. One robustness change was also needed: `LLM.text` returns the empty string on any API failure, and a reasoning-enabled backbone can spend its whole completion budget before emitting any content, on which upstream stores the full reconstructed trajectory as the experience — here a slab of raw transcript — and because `recall` clips from the tail, a single such entry crowds every later experience out of the prompt; REVOKE stores a short deterministic stub built only from the probe text, which is already the embedded retrieval key, and the action taken, and counts every occurrence so a run can be audited for how many of its experiences are stubs rather than summaries.

## MEMP

Memp (Fang et al., 2025, arXiv:2508.06433) treats memory as procedural: each solved task leaves one record holding the task text, a high-level script under 100 words abstracted from the trajectory, and a concrete-steps summary under 150 words of the same trajectory, and a new task retrieves the nearest record by cosine similarity between task-text embeddings. A trajectory marked as failed is not stored at all; instead the records that were served for that task are rewritten by the LLM to absorb the lesson, which is the mechanism by which the method retires a procedure that no longer works. EvolveLab's `MempMemoryProvider` is vendored byte-identical and subclassed at four seams — the LLM hook, embeddings, initialisation and JSON persistence — so the prompts, record format, retrieval rule and add/adjust logic are upstream's code. `observe` writes nothing and makes no call, keeping departed sessions in a rolling 3,000-token buffer that becomes the observation steps of the next trajectory; `recall` embeds the probe text, places the top-1 record in the prompt as upstream formats it, and caches the ids served for that exact query as upstream does; `record_action` assembles the trajectory from the buffer, the agent's rationale and the act call, and distils it into a new record with two backbone calls. The unknown outcome bites hardest here, because upstream's `take_in_memory` branches on it directly: with no correctness signal every trajectory takes the add path, the store grows by one record per probe, wrong actions are distilled into scripts exactly as right ones are, and the revision mechanism the method relies on never fires. Upstream's concrete-summary prompt prints `Correctness: Correct` or `Wrong` from the flag and would label every REVOKE trajectory `Wrong` in its absence, so that one line reads `Unknown` instead; it is the only prompt text changed anywhere in the adapter. An optional variant, `adjust_on_repeat`, is off by default and reported separately where used: when the same probe stem recurs within an episode and the agent now picks a different option, the trajectory is handed to upstream's failure branch so that `_adjust_memory` rewrites the record that was served rather than adding a new one — a proxy for failure and not ground truth, since in REVOKE the licensed option legitimately changes as rules are issued and revoked, so a changed action is weak evidence of a mistake. As with DILU, an empty or placeholder distillation reply is replaced by a short bounded stub built from the probe text and the action taken, rather than upstream's literal placeholder string as the script and the raw session buffer as the concrete-steps summary, which would otherwise be served back to the agent as a procedure to follow.

## What this comparison can and cannot show

All six systems are being asked to do something none of them was built for. mem0 and MemOS are tuned for question-answering recall over a user's history and are scored here on whether a rule base stays current, which is a different problem: a rule and its later revocation are both faithful facts, mem0's default pipeline is add-only and MemOS's `general_text` path has no conflict resolution at all, so in both the two coexist and are ranked against the probe by similarity rather than by time. The unknown-outcome adaptation is the sharpest limit on what a number from this table means. DILU and MEMP both branch on task success upstream — MEMP does not store a failed trajectory but rewrites the record that produced it, and DILU labels each experience correct or wrong before summarising it — and REVOKE's blind protocol removes that branch entirely, so both are measured with their experience-filtering step disabled; that is a deliberate choice, because a benchmark that told the agent when it had violated a rule would be measuring error correction rather than memory invalidation, but it means a result here is evidence about these methods in the no-feedback regime and not a ranking of the published systems on the tasks they were built for. Cost is likewise not comparable across the six on a single axis: DILU makes one backbone call per probe and MEMP two, where Generative Agents made 2,096 and 3,378 memory calls on the two episodes measured offline, so a violation-rate difference and a token-cost difference have to be read separately rather than traded off against each other. Finally, every deviation recorded above is a deviation from a published method, and where one was forced — a truncated curator reply that would wipe a cheatsheet, an empty distillation that would store raw transcript as a procedure — the adapter counts the occurrence in `stats()`, so a reader can tell how often a reported result rested on the adaptation rather than on the method.
